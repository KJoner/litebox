# LiteBox 运维手册

面向已经部署好 LiteBox 的日常运维。安装步骤见 `README.md`,
技术背景见 `docs/开发计划/v1/Phase0-技术验证报告.md`。

---

## 1. 最重要的一件事:主密钥

主密钥(`LITEBOX_MASTER_KEY`)加密了数据库中的**用户 UUID** 与**节点 REALITY 私钥**。

**丢失主密钥 = 丢失全部用户与节点凭据。** 数据库还在,备份也还在,
但里面的 UUID 与私钥全部解不开,只能重建所有用户、重新分发订阅、重装所有节点。

因此:

* 主密钥保存在 `/etc/litebox/litebox.env`(权限 0600);
* 安装后立刻把它抄写到**另一个地方**(密码管理器、离线介质);
* 备份数据库时**不会**带上主密钥,两者必须分开保管且都能取回;
* 恢复备份时必须用**配套的那一把**密钥 —— 不匹配时服务能启动,
  但读取用户与节点会报解密失败。

自检一次:

```bash
# 停掉服务,用错误的密钥启动,应当在读取节点时报错而不是静默工作
LITEBOX_MASTER_KEY=$(litebox genkey) /opt/litebox/litebox check --config /etc/litebox/litebox.yaml
```

## 2. 日常命令

```bash
systemctl status litebox            # 服务状态
journalctl -u litebox -f            # 实时日志
journalctl -u litebox | grep 初始密码 # 首次安装后取初始管理员密码

/opt/litebox/litebox check  --config /etc/litebox/litebox.yaml   # 数据库自检
/opt/litebox/litebox backup --config /etc/litebox/litebox.yaml   # 手动备份
/opt/litebox/litebox reset-password --config /etc/litebox/litebox.yaml  # 忘记密码
```

`litebox check` 做两件事:`integrity_check` 查页面级损坏,
`foreign_key_check` 查引用完整性。后者必要,因为 SQLite 的外键约束
可以在运行时被关掉,历史上一次未开启约束的写入会留下潜伏的坏引用。

## 3. 备份与恢复

### 自动备份

```bash
cp deploy/systemd/litebox-backup.{service,timer} /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now litebox-backup.timer
systemctl list-timers litebox-backup      # 确认下次执行时间
```

每日一次,保留最近 14 份,落在 `/var/lib/litebox/backup/`。

### 为什么不能直接 cp 数据库文件

开启 WAL 后,数据库的最新状态分布在 `litebox.db` 与 `litebox.db-wal` 两个文件里。
直接 `cp` 主文件会得到一份**缺少最近事务、甚至处于半写状态**的副本。

`litebox backup` 用 `VACUUM INTO`,在一个读事务里生成自洽的副本。
这一点有测试覆盖:写入 50 条不做 checkpoint 的记录后备份,50 条必须全在。

### 恢复

```bash
./scripts/restore.sh /var/lib/litebox/backup/litebox-20260802-120000.db
```

脚本会**先校验备份文件本身**再动现有数据库 —— 顺序反了就会用一份坏备份
换掉一个还能用的数据库。恢复前的数据库会被另存为 `before-restore-<时间戳>.db`。

### 备份之外还要留什么

| 内容 | 位置 | 说明 |
|---|---|---|
| 主密钥 | `/etc/litebox/litebox.env` | 最关键,单独异地保存 |
| 配置 | `/etc/litebox/litebox.yaml` | 可重建,但省事 |
| 节点 SSH 私钥 | 已加密存在数据库里 | 备份即包含 |
| sing-box 二进制 | `/opt/litebox/assets/singbox/` | 可用 `scripts/build-singbox.sh` 重建 |

## 4. 升级

```bash
BINARY=./litebox-linux-amd64 ./scripts/upgrade.sh
```

顺序是**先备份 → 换二进制 → 迁移 → 启动 → 健康检查 → 自检**。
备份放最前面,因为迁移不可逆:一旦新版本的迁移执行完,
想回退到旧二进制就只能靠这份备份。

任一步失败,脚本会自动回退二进制并重启。健康检查看的是
`/api/health` 是否真的可用,而不是只看 systemd active。

升级前的备份与旧二进制都留在 `/var/lib/litebox/backup/`。

## 5. 故障处理

### 面板打不开

```bash
systemctl status litebox
journalctl -u litebox -n 50
curl -fsS http://127.0.0.1:8080/api/health
```

常见原因:主密钥未配置或格式错(启动时立刻报错)、
端口被占、数据库文件权限不对(应为 `litebox:litebox` 0600)。

### 节点显示离线 / 同步失败

面板的「仪表盘 → 流量同步」会列出同步失败的节点。逐项排查:

1. **节点详情 → 测试 SSH** —— 不通就是网络或密钥问题;
2. 通了但同步仍失败 —— 多半是节点上的 sing-box 没在跑:
   `ssh 节点 systemctl status litebox-singbox`;
3. sing-box 在跑但 API 不通 —— 检查配置里的 `api_port`
   与节点上实际监听的端口是否一致。

**同步失败不会破坏已入库的流量。** 采样完全在数据库事务之外完成,
读取失败时一个字节都不会动。期间产生的流量会在节点恢复后的下一次同步补记 ——
但仅限于 sing-box 进程没有重启过;进程退出会让未同步部分永久丢失。

### 节点上的 sing-box 崩溃或被 OOM 杀掉

systemd 的 `Restart=on-failure` 会自动拉起,几秒内恢复。
未同步窗口内的流量会丢失(计数器是纯内存的),最大损失为一个同步周期(默认 60 秒)。

面板会在下一次同步时通过 uptime 判定识别出重启,把基线归零,
累计流量既不回退也不漏算。

### 节点配置被人手工改过

节点详情 → **比对配置**,会读回节点上的实际文件与期望状态对比。
不一致时点**部署**,期望状态会覆盖回去。

### 部署失败

部署记录页可展开步骤明细,每一步都有耗时与详情。常见情况:

| 失败步骤 | 含义 |
|---|---|
| 同步流量 | sing-box 在跑但 API 不通,已中止部署以避免流量丢失 |
| sing-box check | 配置本身有问题,**服务未被重启**,当前用户不受影响 |
| 健康检查:VLESS 拨测 | 配置能加载、端口在监听,但用户实际连不上,已自动回滚 |

最后一种最值得留意:只看 systemd 状态与端口监听会把这种节点判为健康,
拨测是唯一能发现它的手段。

### 用户连不上

1. 用户状态是否为「正常」—— 停用、过期、流量用尽都会被从节点配置中移除;
2. 节点详情 → 比对配置,确认该用户在期望用户列表里且 `in_sync` 为真;
3. 用户详情 → 订阅拉取,确认用户真的导入过订阅;
4. 节点详情 → 部署,重新下发一次配置。

## 6. 安全要点

### 已经做到的

* 主密钥加密用户 UUID 与节点 REALITY 私钥;
* 订阅 Token 存 SHA-256 哈希用于查找,公开路由不解密任何字段;
* 会话 Token 只存哈希,明文仅在 HttpOnly Cookie 中;
* 管理员密码用 argon2id;
* 节点 SSH 主机密钥 TOFU 固定,不一致直接拒绝连接;
* 节点上的 V2Ray API 只监听回环,经 SSH 通道访问;
* systemd 单元关闭了全部 capability,`ProtectSystem=strict`。

### 需要你配合的

**订阅地址等同于凭据。** 它出现在 URL 里,因此:

* Nginx 必须对 `/sub/` 关闭 `access_log`(示例配置已包含)——
  否则 Token 会明文落进日志、被日志备份与采集带走;
* 通过 IM 发送订阅地址时注意对方的消息留存策略;
* 用户换设备后如有疑虑,面板可一键重新生成订阅地址,旧地址立即失效。

**节点 SSH 密钥。** 用 `scripts/setup-node-key.sh` 生成一把只给面板用的密钥。
面板需要节点 root 权限(装 systemd 单元、重启服务),这个权限收不掉,
能收的是爆炸半径:专用密钥泄露时不必动你的日常密钥,节点侧也能单独吊销。

**反代必须开 HTTPS**,且配置里 `secure_cookie: true`。
否则会话 Cookie 不带 Secure 属性,可能在明文连接上泄露。

## 7. 容量与限制

实测数据(Debian 12,2C2G;节点为同机 128MB cgroup 限制):

| 项目 | 实测 |
|---|---|
| 节点内存(空闲) | cgroup 约 10 MB |
| 节点内存(10 用户并发负载) | 见 Phase 7 压测结果 |
| 主控二进制 | 19 MB(含前端) |
| 节点二进制 | 27.8 MB(精简构建) |
| SSH 建连 | 约 1.3 秒,之后调用约 157 ms |
| 流量计量误差 | 约 +0.34%(协议开销,宁多勿少) |

**设计上的硬限制:**

* **一台机器只能承载一个节点** —— 节点上的路径(`/opt/litebox`)
  与服务名(`litebox-singbox`)是固定的,两个节点指向同一主机会互相覆盖配置;
* **REALITY 握手目标的 TLS 记录必须 ≤ 8192 字节** —— 新增节点时
  用「扫描握手目标」实测,微软系站点因证书链过大不可用;
* **用户变更需要重启 sing-box 才生效** —— VLESS 用户列表无法热更新,
  面板会把连续变更合并成一次重启(默认静默 4 秒);
* **未同步窗口内的流量不可恢复** —— 意外重启最多丢一个同步周期的流量;
* **改节点访问等级会立刻触发重新部署** —— 与改端口不同,这一条不等你挑时机。
  等级调高后被移出的用户凭据还留在节点上,不重新部署等于权限没收回。
  请在低峰时段操作;
* **节点资源采样只保留 7 天** —— 那是看趋势用的,不是计费数据。
  趋势图的 168 小时就是上限,给更长的选项只会看到一段被清理掉的空白。

## 8. 定期检查清单

**每月:**

* [ ] `litebox check` 自检通过
* [ ] 确认自动备份在跑:`systemctl list-timers litebox-backup`
* [ ] 随机取一份备份做一次恢复演练(可在另一台机器上)
* [ ] 确认主密钥的异地副本仍能取回

**每次升级前:**

* [ ] 确认有一份当天的备份
* [ ] 记下当前版本号,便于回退

**用户门户相关:**

* [ ] 新开通门户账号时勾上"要求首次登录后修改密码" ——
      在改掉之前用户拿不到订阅地址,初始口令泄露的窗口就只有一次登录;
* [ ] 用户报告设备丢失时,在用户详情里点「踢出全部」;
      怀疑密码泄露则改密码,那会连带撤销全部会话;
* [ ] 停用某人的门户登录**不影响他的代理连接** ——
      要断代理请用用户列表里的「停用」。

**新增节点后:**

* [ ] 扫描握手目标并确认记录长度有余量
* [ ] 探测结果中 `has_v2ray_api` 为真
* [ ] 部署一次并确认拨测步骤通过(而不是被跳过)
* [ ] 确认访问等级设对了 —— 默认是普通组,也就是所有人都能用
