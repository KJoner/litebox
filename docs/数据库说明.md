# LiteBox 数据库说明

只用 SQLite,单文件,WAL 模式。表结构由 `internal/database/migrations/` 下的
迁移脚本定义,按版本号顺序应用。

## 迁移规则

* **只能新增迁移文件,不得修改已应用的迁移。** 迁移框架会记录每个文件的
  SHA-256,内容变了直接拒绝启动 —— 不同环境的库结构悄悄分叉是最难查的一类问题;
* 文件名形如 `0007_access_tiers.sql`,版本号连续;
* 每个迁移在单个事务内执行,要么全成功要么全回滚;
* 迁移是幂等的:已记录在 `schema_migrations` 里的版本会被跳过,
  因此一键脚本每次部署都跑一遍没有副作用。

```bash
go run ./cmd/litebox migrate   # 只执行迁移并做一致性检查
```

## 全局约定

* 所有时间列存 **UTC 的 RFC3339 字符串**(`2026-08-03T12:00:00Z`);
* 所有流量列单位为**字节**;
* 需要还原的敏感字段(用户 UUID、节点 REALITY 私钥、节点 SSH 私钥、
  面板专用私钥、订阅 Token)存**主密钥加密后的密文**;
* 会话 Token 与订阅 Token 的查找路径只用 **SHA-256 哈希**,不解密任何字段;
* 用户与节点用**软删除**(`deleted_at`),`user_code` 不回收也不复用。

## 核心表

### access_tiers —— 节点访问等级

| 列 | 说明 |
| --- | --- |
| `code` | `normal` / `vip` / `root`,**程序内一律用它判断**,不要用 `name` |
| `name` | 展示名称,管理员可改 |
| `level` | 10 / 20 / 30。节点 `level <= 用户 level` 即可用 |
| `description` `sort_order` | 展示用 |

V2 不提供新增与删除等级,只允许改名称、说明与排序。`code` 与 `level` 不可改 ——
改 `level` 会让所有用户可用的节点集合同时变化,而页面上看不出发生了什么。
留出 10 的间隔是为了以后插入 SVIP 之类的等级时不必重排。

### user_effective_nodes —— 有效节点视图(最重要的一处)

```sql
CREATE VIEW user_effective_nodes AS
    -- 1. 等级继承:节点等级不高于用户等级
    SELECT u.id, n.id FROM proxy_users u
      JOIN access_tiers ut ON ut.id = u.access_tier_id
      JOIN nodes n ON n.deleted_at IS NULL
      JOIN access_tiers nt ON nt.id = n.access_tier_id
     WHERE u.deleted_at IS NULL AND nt.level <= ut.level
    UNION
    -- 2. user_nodes 里管理员单独追加的节点
    SELECT un.proxy_user_id, un.node_id FROM user_nodes un ...;
```

**配置生成、订阅生成、用户门户、额度检查与部署脏标记全部查这张视图。**
这是"用户能用哪些节点"的唯一定义。四处各写一份等级判断迟早会分叉,
而分叉的表现是用户在订阅里看得到、连上去却没有凭据,全链路不报任何错。

规则若要变更,必须新增迁移 DROP 后重建视图,不得改动 0007。

### proxy_users —— 代理用户

V2 新增 `access_tier_id`(NOT NULL DEFAULT 1)。存量用户一律落在普通组,
升级后可用节点集合与升级前完全一致。

这一列刻意没写 `REFERENCES`:SQLite 的 `ALTER TABLE ADD COLUMN` 在
`foreign_keys` 打开时要求带外键的新列默认值必须是 NULL,而这里必须
`NOT NULL DEFAULT 1` 才能让存量行直接落到普通组。完整性改由视图的
INNER JOIN 与 `access.Store.Validate` 保证。

### nodes —— 节点

V2 新增:

| 列 | 说明 |
| --- | --- |
| `access_tier_id` | 节点所属等级,默认普通组 |
| `display_name` | **对用户与订阅展示的名称**;`name` 是内部名称,只在管理后台出现 |
| `sort_order` | 订阅与门户中的排序,数值小的在前 |
| `subscription_enabled` | 关掉后不再进入新生成的订阅,节点与历史数据全部保留 |
| `public_remark` | 用户可见说明 |
| `maintenance_message` | 节点维护提示 |

升级时 `display_name` 从 `name` 复制。不能留空 —— 订阅里的节点名是客户端
识别条目的依据,升级后突然变空会让客户端把它当成新节点重复添加。

`proxy_port` 与 `listen_port` 的区别见 CLAUDE.md:前者是客户端连接的公网端口,
只写进订阅;后者是 sing-box 的 `inbound.listen_port`。

V2.1 新增(迁移 0011):

| 列 | 说明 |
| --- | --- |
| `ipv6_address` | 可选的公网 IPv6,**只影响订阅**;空串表示该节点只有 IPv4 |
| `traffic_quota_bytes` | 节点流量额度,0 表示不限量 |
| `traffic_reset_cycle` | `NONE` / `MONTHLY`,列上有 CHECK 约束 |
| `traffic_reset_day` | 每月重置日 1~31,列上有 CHECK 约束 |

`host` 的业务含义随之明确为 **IPv4 地址及 SSH 管理地址**。列名没改 ——
重命名一个已被十几处 SQL 引用的列,收益只是名字好看一点。

`ipv6_address` 存**标准化后的无方括号形式**(`2602:fed2::1`)。方括号是
URI 语法的一部分,不是地址的一部分:存带括号的值会让 sing-box 客户端配置的
`server` 字段变成 `"[2602::1]"`,客户端解析不出地址,而订阅本身照常下发。

**IPv6 没有单独的 nodes 记录。** 订阅生成时由 `subscription.PhysicalNode.Expand`
把一条记录展开成一到两个条目。拆成两行会带来第二份 `config_revision`、
第二串 `deployments` 与第二套 `node_metrics`,而机器只有一台。

迁移 0012 新增一列:

| 列 | 说明 |
| --- | --- |
| `ipv6_proxy_port` | IPv6 条目在订阅里用的公网端口,**0 表示跟随 `proxy_port`**;列上有 `BETWEEN 0 AND 65535` 的 CHECK |

**那个 0 必须原样留在库里,不能在写入时就解析成当时的 `proxy_port`。**
写死的话,之后把公网端口从 443 改成 8443,IPv6 条目会继续停在 443 上 ——
而管理员当初看到的是一个空输入框,完全不会想到那里固化了一个值。
解析发生在 `Expand` 里,与展开逻辑在同一处。

`listen_port` 仍然只有一个:两条链路指向同一个 sing-box 入站,
IPv6 端口只是外部映射的另一个号码。清空 `ipv6_address` 时这一列一并归零。

迁移 0013 新增一列:

| 列 | 说明 |
|---|---|
| `traffic_billing_mode` | `EGRESS`(只计出站,×1)/ `BOTH`(进出合计,×2);列上有 CHECK 约束,默认 `EGRESS` |

sing-box 的 `uplink`/`downlink` 计的是**客户端↔节点这一段**的双向字节,
而一次用户下载在节点网卡上要走两趟(从源站收一份、再发给客户端一份)。
所以按进出合计计费的机器,VPS 商看到的数字约是 sing-box 计数的两倍。

**不写死成某一个倍数**:两种口径都常见,甚至同一家不同套餐都不一样。
一律 ×2 会让按出站计费的机器高报一倍 —— 额度还剩一半面板就报红,
而管理员没有任何办法看出这是口径问题还是真的用超了。默认 `EGRESS`,
存量节点的显示与告警与升级前一个字节都不差。

**折算只发生在读取时**(`traffic.buildNodeCycleUsage`),
`traffic_ledger` 与 `proxy_users.used_*` 一个字节都不动。用户额度也不受影响 ——
那算的是用户自己用了多少,与主机怎么计费无关。改这一列不触发重新部署。

**周期重置不删除任何数据。** `traffic_ledger`、`traffic_daily`、
`proxy_users.used_*` 与 `node_counters` 全部原样保留,当前周期用量是按
`node_id` + `created_at` 范围现算的。因此改重置日、改周期都不会毁掉历史报表,
改回去也能还原。汇总走已有的 `idx_traffic_ledger_node(node_id, created_at)`,
没有新建索引。

### portal_accounts / portal_sessions / portal_login_attempts

普通用户的登录账号、会话与登录失败记录。与管理员的 `admin_users` /
`admin_sessions` / `login_attempts` 是完全独立的三张表。

不把普通用户塞进 `admin_users`:那张表的每一行都能进后台,一次判断写漏
就等于把管理权限发给了代理用户。登录失败记录也分开 —— 混在一起时,
门户被撞库会连带把管理员登录锁死。

`portal_accounts.login_enabled` 是**唯一**能挡住门户登录的开关。
代理服务过期或超额的用户仍要能登录,否则他连"为什么断了"都看不到。

`proxy_user_id` 上的外键是硬删除才触发的;代理用户用软删除,所以登录与
会话校验都额外 JOIN `proxy_users` 并要求 `deleted_at IS NULL`。

### user_adjustments —— 人工续期与额度调整

系统没有支付与订单,这张表只回答"是谁、在什么时候、给谁加了多少流量或
延了多少天"。刻意不叫"充值记录" —— 没有真实支付,那个词会让用户以为
自己付过钱。

与 `audit_logs` 的分工:审计日志记"发生了什么操作",面向排查,会按时间
轮转清理;这张表记"额度与期限怎么变的",面向对账,必须长期可查,
而且其中一部分要给用户看。

`remark` 是唯一对用户公开的文字,不要往里写内部说明。

### node_metrics —— 节点资源采样

只保留一段滚动窗口(默认 7 天)。这是运维看趋势用的,不是计费数据,
丢了不影响任何结算,而无节制增长会把 SQLite 撑大。

采集间隔默认 5 分钟,比流量同步(60 秒)宽得多 —— 节点上每次只跑一条
shell,128MB 的小机器也吃得住。

## 升级兼容

V1 库直接升级到 V2 是无损的,由 `internal/database/upgrade_test.go` 守着:

1. 初始化 NORMAL / VIP / ROOT 三个访问等级;
2. 存量用户与存量节点默认设为 NORMAL;
3. 存量节点的 `display_name` 复制现有 `name`;
4. 存量节点默认 `subscription_enabled = 1`(默认关掉会让所有人的订阅瞬间清空);
5. 保留全部 `user_nodes` 作为额外授权;
6. 不修改存量用户 UUID、订阅 Token、流量 ledger 与累计流量;
7. 不影响现有管理员账号及会话;
8. 重复执行迁移不会重复插入等级。

## 备份

```bash
litebox backup            # WAL 安全的数据库备份
litebox check             # 完整性与外键自检
```

**数据库备份不含主密钥。** 主密钥在 `/etc/litebox/litebox.env`,
丢失后用户 UUID 与节点 REALITY 私钥不可恢复,必须单独备份。
