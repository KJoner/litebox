## 3. 核心业务变更审查

| 项 | 结论 |
|---|---|
| 配置一致时跳过重部署 | 判据(`node.Preflight` 第 7 步):渲染哈希 = 库里上次下发的哈希 = 节点上配置文件的哈希,**且**服务在跑;四项任一不满足都照常下发。这套逻辑自 V20 起已在协调器、批量部署与 `/deploy` 接口上生效,本轮只是让卡片按钮不再误传 `force`。**发现一处连带问题并已修复**:它不看二进制,重新安装 sing-box 后配置没变时普通下发会被跳过,而原提示让人「点一次下发配置」—— 已改为指向「强制重新下发 / 重启」(`6253b43`)。**测试缺口**:跳过判据没有单元测试,本轮用真机补了正反两条证据(见第 5 节) |
| 部署记录读失败 | 失败时保留上一次结果并注明;没有旧数据时显示错误态与重试,不再显示「还没有部署记录」。换节点时错误标记一并清掉 |
| 同步失败记录清理 | 只在一轮开始、拿到同步名单之后清掉**不在名单里**的机器(已删除、停用、待部署、云实例停机);名单查询失败时整轮返回、不清任何记录;仍在名单里的失败保留,有单测钉着 |
| 仪表盘并行加载与重试 | 各来源独立加载,失败保留旧数据;「重试失败项」只重跑失败的加载函数并去重;按钮在加载中不可重复点。**低风险竞态**:「刷新」与「重试」同时进行时,同一接口可能有两个请求并发,后返回的覆盖先返回的 —— 两者都是新数据,只影响毫秒级先后,不阻塞发布 |
| 门户流量 | 只改标签与说明,`internal/portal` 一行未改;升级前后三种订阅输出逐字节一致 |
| 入口管理 / 路由 / 权限 / 按钮 | 路由与守卫未改;49 处链接式操作换成 `RouterLink` / `button`,事件处理函数原样保留,按钮绑定逐个核对过(唯一带参数的 `deploySingBox` 已修);操作列固定只改布局 |
| 数据库与 API 兼容 | 无迁移;`/api/traffic/status` 只加 `running`、`last_started`、`failed_at` 三个字段,新前端对旧后端缺字段有兜底 |

## 5. 预发布验证(测试数据库副本)

在本机用 scratch 面板数据库的副本演练,两个二进制都从 LF 检出构建(与服务器上一键脚本的构建方式一致):

| 步骤 | 结果 |
|---|---|
| 旧版(`7790978`)启动、只读验收 | 健康检查、管理员与门户登录、14 个管理接口、5 个门户接口、三种订阅输出全部正常 |
| 运行中 `litebox backup` | 生成 WAL 安全的备份,旧二进制另存 |
| 停服 → 新版 `migrate` | 数据库已是最新(版本 38),无迁移执行,一致性检查通过 |
| 新版启动、只读验收 | 同上全部正常;`check` 通过;**三种订阅输出与旧版逐字节一致**;同步状态接口多出 `running` 字段 |
| 授权测试节点 · 配置一致的下发 | 返回「配置已一致」,下发步骤 SKIPPED,节点上 sing-box 进程号与运行时长不变 |
| 授权测试节点 · 配置有变化的下发 | 在副本里把上次下发哈希改掉模拟「库里配置已变化」:前置检查判为需要下发 → 替换配置 → 重启(进程号变化)→ 真实拨测通过;因为内容实际没变,下发后记录的哈希回到原值 |
| 回滚:旧二进制直接起在升级后的库上 | 全部正常,三种订阅与升级前逐字节一致 |
| 备份可用性 | 升级前备份能被旧版打开并通过 `check` |

**演练中发现的既有隐患(与本轮无关)**:迁移文件的内容哈希不忽略换行符。仓库存的是 LF,
但在 `core.autocrlf=true` 的 Windows 工作区里构建的二进制会把被重新检出过的迁移算成 CRLF 哈希。
用这种二进制初始化或迁移过的数据库,换成服务器上(LF)构建的版本时 `migrate` 会报
「迁移内容在应用后被修改」并拒绝启动;`upgrade.sh` 会自动回退旧二进制,不会坏库,但升级会失败。
生产是在服务器上用一键脚本构建的话不受影响。建议后续加 `.gitattributes`(`*.sql text eol=lf`),
本轮不改。

## 6. 升级步骤(合并 master 之后)

**合并 master 即发布**:一键脚本 `litebox-install.sh` 用 `git fetch origin master && reset --hard`
更新源码后现场构建,再调用 `upgrade.sh`。

1. **升级前**:确认生产当前是用一键脚本在服务器上构建的(否则先按第 5 节的隐患,用新版二进制对
   数据库副本跑一次 `litebox migrate`);另存一份 `/etc/litebox/`(`litebox.yaml` 与含主密钥的
   `litebox.env`)—— `upgrade.sh` 只备份数据库与旧二进制,主密钥要与备份分开保存
2. **升级**:在主控上重跑一键脚本(或 `make build-linux` 后 `BINARY=bin/litebox-linux-<arch> scripts/upgrade.sh`)。
   脚本会:运行中备份数据库 → 另存旧二进制 → 停服换二进制 → `migrate`(本轮为空操作)→ 启动 →
   `/api/health` 检查 → `check`;任一步失败自动换回旧二进制
3. **验收**:管理员与门户登录;节点列表、巡检、仪表盘;拉一次订阅;在**测试节点**上点一次「下发配置」,
   确认配置一致时返回「配置已一致」而不重启
4. 已打开的面板标签页刷新一次
5. `npm ci` 会多装开发依赖 `@playwright/test`(纯 JS,不下载浏览器),构建产物不含测试代码

## 7. 回滚步骤

本轮**没有数据库迁移,也不改节点配置的渲染**,所以回滚只是换回二进制,不需要恢复数据库、
不需要重新部署任何节点。

1. 换回旧二进制(`upgrade.sh` 已把它存在数据库目录的 `backup/litebox-<时间戳>.bin`):
   ```bash
   systemctl stop litebox
   install -m 0755 /var/lib/litebox/backup/litebox-<时间戳>.bin /opt/litebox/litebox.new
   mv /opt/litebox/litebox.new /opt/litebox/litebox
   systemctl start litebox
   curl -fsS http://127.0.0.1:<端口>/api/health
   ```
2. **只有在想丢弃升级之后产生的数据时**才恢复数据库:`scripts/restore.sh <pre-upgrade-*.db>`
   (会先自检备份、要求输入 yes;升级后新增的流量账本、部署记录会丢失,主密钥必须是同一把)
3. 代码层面:`git revert` 合并提交只影响**之后**用一键脚本安装 / 更新的机器;已经升级的机器按第 1 步换二进制
4. UI 2.0 五批已在 master 上;若连它也要回退,需要回退那五个提交 —— 同样没有迁移,换二进制即可
