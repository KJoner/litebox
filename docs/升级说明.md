# LiteBox 升级说明

## V1 → V2

V2 增加了普通用户门户、三档节点访问等级与节点展示名称。**存量库可以直接
升级,不需要任何手工数据处理。**

### 升级前

```bash
# 备份数据库(升级脚本也会自动做一次,但自己留一份更稳)
sudo -u litebox /opt/litebox/litebox backup --config /etc/litebox/litebox.yaml

# 确认主密钥还在,并且你手上有一份
sudo cat /etc/litebox/litebox.env
```

主密钥丢失后用户 UUID 与节点 REALITY 私钥不可恢复,数据库备份救不回来。

### 执行升级

一键脚本部署的:

```bash
bash <(wget -qO- https://raw.githubusercontent.com/KJoner/litebox/master/scripts/litebox-install.sh)
```

手工部署的:

```bash
sudo ./scripts/upgrade.sh
```

两者都会先备份、再替换二进制、启动时自动执行迁移;失败自动回退。

### 升级做了什么

新增四个迁移(0007~0010):

| 迁移 | 做的事 |
| --- | --- |
| 0007 | 建 `access_tiers` 并写入 NORMAL/VIP/ROOT;给用户与节点加 `access_tier_id`;建 `user_effective_nodes` 视图 |
| 0008 | 给节点加 `display_name` 等对外字段,并把 `display_name` 从 `name` 复制过来 |
| 0009 | 建 `portal_accounts` / `portal_sessions` / `portal_login_attempts` |
| 0010 | 建 `user_adjustments` |

### 升级后会发生什么变化

**默认什么都不变。** 存量用户与存量节点全部落在普通组,而普通组用户本来
就能用到全部普通组节点 —— 升级后每个用户的可用节点集合与升级前完全一致。
`internal/database/upgrade_test.go` 逐条守着这一点。

具体地:

* 订阅内容不变。节点名沿用原来的名字(`display_name` 复制自 `name`),
  客户端不会把它当成新节点重复添加;
* 订阅地址不变,用户不需要重新导入;
* 流量、ledger、累计用量、部署记录一行不动;
* 管理员账号与已登录的会话不受影响;
* `user_nodes` 里的分配关系全部保留,继续作为"额外授权"生效;
* 没有任何用户拥有门户登录账号 —— 门户要由管理员逐个开通。

### 升级后建议做的三件事

**1. 给节点分组(可选)**

节点管理 → 编辑 → 访问等级。不改就是所有人都能用,与升级前一样。

改等级会**自动触发重新部署**(会重启该节点的 sing-box,断开在线连接),
因为等级调高后被移出的用户凭据还留在节点上,不重新部署等于权限没收回。
挑一个低峰时段做。

**2. 把内部名称与展示名称分开(可选)**

如果节点的内部名称里写了机房、供应商、到期日这类运维信息,现在可以把
`name` 改成运维视角的名字,`display_name` 留给用户看。改 `display_name`
不需要重新部署,但客户端要更新一次订阅才会看到新名字。

**3. 开通门户登录(可选)**

用户管理 → 详情 → 门户登录 → 开通。设一个账号名和初始密码,勾上
"要求用户首次登录后修改密码",然后把 `https://你的域名/user/login`
和初始密码通过安全渠道发给用户。

不开通也完全不影响使用 —— 用户照常用订阅地址。

### 回滚

升级脚本在替换前会备份数据库与旧二进制。若要回到 V1:

```bash
sudo ./scripts/restore.sh /var/backups/litebox/litebox-<时间戳>.db
```

注意 V2 迁移是**单向的**:V1 的二进制读 V2 的库会因为 `schema_migrations`
里有它不认识的版本而正常运行(迁移框架只跳过已应用的版本),但 V2 新增的
列与表对它没有意义。稳妥做法是二进制与数据库一起回滚。

## V2 → V2.1

V2.1 增加了节点的可选 IPv6 订阅地址,以及节点级的流量额度与重置周期。
**存量库直接升级,不需要任何手工数据处理,行为一个字节都不变。**

升级方式与下面的「日常升级」完全相同。

### 升级做了什么

新增一个迁移(0011),给 `nodes` 加四列:

| 列 | 默认值 | 含义 |
| --- | --- | --- |
| `ipv6_address` | `''` | 空串即 IPv4-only,与升级前一致 |
| `traffic_quota_bytes` | `0` | 0 即不限量 |
| `traffic_reset_cycle` | `'NONE'` | 不重置,统计创建以来的累计流量 |
| `traffic_reset_day` | `1` | `NONE` 时不起作用 |

`host` 的业务含义明确为「IPv4 地址及 SSH 管理地址」,列名没有改动,
所有存量数据原样保留。

### 升级后会发生什么变化

**默认什么都不变。** 存量节点全部是 IPv4-only、不限量、不重置:

* 订阅内容一条不多一条不少,用户不需要重新导入;
* SSH、探测、安装、部署、重启、流量同步、资源采集全部照旧走 `host`;
* 流量统计、ledger、每日汇总、部署记录一行不动;
* 节点列表多出一列「周期流量」,不限量节点显示为「已用量 / 不限量」。

一个例外值得知道:**用域名接入的存量节点**在编辑时,只要不改「IPv4 地址」
这一栏就照常保存;真要改这一栏时会要求填 IPv4 字面量。

### 升级后可以做的两件事

**1. 给双栈节点填上 IPv6(可选)**

节点管理 → 编辑 → IPv6 地址。填完保存即可,**不需要重新部署**,
也不会断开任何在线连接。订阅里随即多出一条 `展示名称-IPV6`,
用户的客户端下次更新订阅就能看到。

清空这一栏则把该条目撤下来,同样即时生效。

**2. 给节点设流量额度(可选)**

节点管理 → 编辑 → 节点流量限额 / 重置周期 / 每月重置日。
周期边界统一取 **UTC 00:00**,页面上标了出来。

额度只用于统计与预警:超额会在仪表盘和节点列表里标红,但**不会**
停掉 sing-box、禁用节点或把节点从订阅里摘掉 —— 流量同步存在时间间隔,
各家 VPS 的计量口径也不一致,自动关掉一个共享节点会同时打断全部用户。

设额度不影响任何历史数据。改重置日、改周期都只是换了统计起点,
`traffic_ledger` 一行都不会删,改回去也能还原。

## V2.1 → V3

V3 是一次整体 UI 改造。**没有数据库迁移,没有配置项变化,没有接口被删除或改名。**
升级方式与下面的「日常升级」完全相同,回滚也只是把二进制换回去。

### 升级做了什么

界面全部重写:统一的设计 Token、状态改成「形状 + 文案 + 颜色」三重编码、
每一页都区分加载 / 空 / 筛选为空 / 失败四种状态。三处接口是新增的,老接口一个没动:

| 接口 / 字段 | 说明 |
| --- | --- |
| `GET /api/traffic/daily` | 新增。全站每日流量,给仪表盘的趋势图 |
| `GET /api/nodes` 的 `config_state` / `needs_deploy` | 新增两个算出来的字段,纯查库,不连 SSH |
| `GET /api/users` 的 `next_reset_at` | 新增。与门户用的是同一份计算 |

有一处**行为**变化值得知道:每日流量序列(全站、按节点、按用户、门户)
不再把没有记录的日子补成 0,只返回确实有记录的那些天。库里没有某一天,
可能是那天真的没人用,也可能是同步任务没跑完 —— 补 0 等于替其中一种下了结论。
现在缺的日子在图上画成空心柱并标明「未知」。历史数据一个字节都没有改动。

### 升级后会看到什么变化

* 侧栏由深色改成白底 + 1px 边线,菜单分成「总览 / 资源 / 运维」三组并带计数;
* 节点列表把「状态」拆成**运行状态**与**配置状态**两列 ——
  一台在跑旧配置、上次部署失败的机器,原来只显示「部署失败」,
  看不出它其实还在正常服务用户;
* 节点详情原来是 12 个同样大小的按钮排成一排(只读的「探测」和会抹掉服务的
  「卸载服务」尺寸完全相同),现在分三层:只读检查在常驻工具条、部署是唯一主按钮、
  会改变节点的收进「⋯」且不可逆的四项在分隔线之下;
* 接口失败时指标卡显示「—」而不是 0。原来读不到和真的是零长得一模一样;
* 手机上打开管理后台,四张长表会换成卡片列表 —— 原来横向滚动会把最右边的
  「操作」列推到屏幕外;
* 用户门户的「订阅不可用」从一条 Alert 改成整块替换,并写清原因与恢复后的行为。

### 体积

前端产物从约 2MB 增加到约 7.3MB,增量全部是自托管的中文字体
(`Noto Sans SC` 两档,按 unicode-range 分片)。面板要 embed 进单个二进制、
也要能在断网内网里跑,所以不引 CDN。浏览器只下载页面上真正用到的那几片,
实际传输量远小于这个数字。

## IPv6 公网端口(V3 之后的增量)

给节点加了一个可选的「IPv6 公网端口」。新增迁移 0012,给 `nodes` 加一列
`ipv6_proxy_port`,默认 0。**存量节点行为一个字节都不变** —— 0 表示
IPv6 条目跟随 IPv4 的 `proxy_port`,与升级前完全一致。

什么时候需要填:双栈机器的两个协议栈映射到**不同**的外部端口时。
NAT 小鸡上很常见 —— IPv4 是服务商映射的高位端口,IPv6 则是直连的 443。
两者相同就一直留空,以后改 IPv4 公网端口,IPv6 会自动跟着变。

节点管理 → 编辑 → IPv6 地址右边那一栏。改完保存即生效,
**不需要重新部署**,也不会断开任何在线连接 —— 它只改订阅内容,
一个字节都不进节点配置。清空 IPv6 地址时这个端口会一并清掉。

## 节点页与图表的一批改动(IPv6 公网端口之后)

**没有数据库迁移,没有配置项变化,没有接口改动。** 升级方式同下,回滚只是换回二进制。

### 会看到什么变化

* **节点列表按排序值升序排列,并把排序值写在名称前面**(`#10`、`#20`)。
  这个顺序与订阅、门户里的顺序是同一个 —— 原来排序值只能在编辑弹窗里看到,
  改完也看不出改到了第几位;
* **「本周期流量」下面多一行重置日**,例如「9 月 1 日 00:00 UTC 重置 · 18 天后」。
  不重置的节点写「不重置 · 累计至今」—— 那一列对它们来说是创建以来的累计量,
  而表头写的是「本周期流量」;
* **流量图可以悬停读数**了。仪表盘的 30 天趋势、节点详情的流量、用户详情的流量、
  用户门户的流量四处都是同一个组件,悬停显示「8 月 2 日 · 28.18 GB」;
  没有记录的日子显示「当天没有记录(不是 0)」;
* **节点详情在只读检查(探测、扫描握手目标等)进行中不再被误关**。
  这些动作要几秒到十几秒,期间点一下抽屉外面就会把它关掉,而结果几秒后才返回 ——
  看起来就是「点了探测,等了一会儿,详情页自己没了」。现在遮罩点击与 ESC 在
  检查期间失效,右上角的 × 照常可用,工具条上会写明正在跑什么;
* **部署的确认框在点「部署」后立刻收起**,不再和进度弹窗叠在一起;
* 编辑节点时,端口转发提醒框下面那行「REALITY 握手目标不在这里改…」不再被压住;
* 节点详情里「已部署配置」从未部署时显示「从未部署」而不是「—」——
  后者在本项目里的含义是「读取失败」。

### 修掉「点一下探测,节点详情就没了」

这是一个后端序列化问题,只在**探测成功**时出现,所以看起来像探测把页面搞崩了。

Go 的 nil 切片序列化成 JSON `null` 而不是 `[]`。探测一切正常时
`problems` 恰恰是 nil,`build_tags` 在 sing-box 没输出 `Tags:` 行时也是。
前端把这两个字段当数组用(`problems.length`、`build_tags.join(',')`),
拿到 `null` 就在渲染期抛异常:抽屉内容整个被卸载,而遮罩是另一个 DOM 节点、
会留在屏幕上 —— 表现为「详情页消失、屏幕一片灰,只能点一下灰色区域才能脱身」。
探测**失败**时 `problems` 有内容,反倒一切正常。

修了三层:后端的 `ProbeResult`、`DestCheckResult` 与部署结果的 `steps`
一律初始化成 `[]`;前端对这些数组加了兜底;抽屉再遇到渲染错误会自己关掉
并说明原因,不再留下点不掉的遮罩。扫描握手目标走的是同一段代码,一起修了。

### 内置的候选握手目标换了

苹果与谷歌系(`www.apple.com`、`dl.google.com`、`gateway.icloud.com`)被移出候选,
换成 `www.fastly.com`、`shopify.com`、`www.tesla.com`、`download.jetbrains.com`;
`addons.mozilla.org` 与 `www.cloudflare.com` 保留。被拿掉的三个 TLS 参数其实都合格,
原因是各类教程都用它们 —— 一台 VPS 常年只跟这几个域名握手本身就是特征。

**存量节点已经在用的握手目标不受影响**,这只改「扫描握手目标」时实测哪几个候选。
新建节点的默认目标从 `www.cloudflare.com` 变成 `www.fastly.com`,而默认值在部署前
本来就该实测确认一次。想换目标:节点详情 →「扫描握手目标」→ 在合适的那一行点「应用」,
应用后需要部署才在节点上生效。

## 自动打开节点的 SSH TCP 转发

**没有数据库迁移,没有配置项变化。**

面板对节点的三件事全都走 SSH 的 direct-tcpip 通道:读 V2Ray Stats API
(流量同步)、从节点出口实测 REALITY 握手目标、部署健康检查里的真实 VLESS 拨测。
`AllowTcpForwarding` 在 OpenSSH 里默认是 `yes`,但不少 VPS 镜像 —— 尤其做过加固的
Alpine 和部分服务商的 Debian 模板 —— 把它关成了 `no`。关掉之后上面三件事**全部**失败,
而 sshd 给的原因只有一句:

```
ssh: rejected: administratively prohibited (open failed)
```

这句话既不提是哪个配置项,也不提该去哪台机器上改。更麻烦的是**命令执行
(session 通道)完全不受影响**,所以「测试 SSH」和「探测」照常通过 ——
看起来只有代理相关的功能坏了,排查方向一开始就是错的。

### 现在会怎么样

* **探测**会实测这项能力并显示出来。关着时给一条**警告**(不是错误):
  sing-box 照常服务用户,节点也不会被判成离线;
* **安装 sing-box** 会在传二进制之前把它打开:往 `/etc/ssh/sshd_config`
  (或 `sshd_config.d/` 下的 drop-in)加一行 `AllowTcpForwarding yes`,
  `sshd -t` 校验通过后 **reload** sshd,再实测一次通道确认真的生效;
* 改动前把原文件备份成 `/etc/ssh/sshd_config.litebox-bak-<时间戳>`,
  **任何一步失败都恢复原样**;改了之后面板会弹窗告诉你改了哪个文件、备份在哪;
* 还没升级、或者你不想让面板碰 sshd 的情况下,现在报错也会直接写明
  是 `AllowTcpForwarding` 的问题以及该怎么改。

### 几个刻意的选择

**reload 不是 restart。** reload 只让 sshd 重读配置,已建立的连接一条不断;
restart 万一起不来,这台机器就再也连不上了,没有任何补救手段。

**只加一行,不删也不注释已有的行。** 那些行可能在 `Match` 块里,是管理员对
特定用户的刻意限制,不该被面板顺手抹掉。加的那一行放在文件**最前面** ——
OpenSSH 对这类关键字取首次出现的值,追加到末尾是完全无效的,而配置文件里
明明白白写着 yes,这种自相矛盾最难查。

**判断靠实测,不靠读配置。** 面板真正需要的能力只有一个 —— 这条通道能不能开起来,
所以就直接开一条到节点本机 sshd 端口的通道试试。`sshd -T` 的输出与实际行为
未必一致(Match 块、多个 Include、版本默认值),而改完配置就宣布成功,
和「部署只看 systemd 状态」是同一类错误。

### 已经装好的节点怎么办

在节点详情里再点一次 **安装 sing-box**。二进制哈希相同时不会重复上传 28MB,
这一步只会补上 sshd 的配置。

## 节点流量的计费口径(迁移 0013)

新增迁移 0013,给 `nodes` 加一列 `traffic_billing_mode`,默认 `EGRESS`。
**存量节点行为一个字节都不变。**

### 解决的问题

sing-box 统计的是**客户端与节点之间**转发的字节。但节点是个中继:一次用户
下载,节点先从源站收 1 份(入),再发给客户端 1 份(出)——网卡上走了两趟。

| VPS 商怎么计量 | 与面板数字的关系 |
|---|---|
| 只计出站 / 上行(egress) | ≈ **1×**,原来就是对的 |
| 进出合计 / 双向(in + out) | ≈ **2×**,原来面板只显示了一半 |

按双向计费的机器,原来面板说用了 500 GB,商家账单上其实已经是 1 TB。

### 升级后怎么用

节点管理 → 编辑 → **计费口径**,按 VPS 商的口径选一次。之后
**流量限额直接填商家给的数字**,面板负责换算:

* 选「双向」后,进度条、剩余量、百分比与告警等级全部按 ×2 之后的量算;
* 节点详情里同时列「代理转发」(sing-box 原始计数)与「主机口径」(折算后);
* 节点列表在那一行标出 `双向计费 ×2 · 代理转发 xxx`;
* 改这一项**不触发重新部署**,也不断开任何连接 —— 它只影响统计与展示。

### 几个刻意的选择

**不做成一律 ×2。** 两种口径都常见,甚至同一家不同套餐都不一样。一律翻倍
会让按出站计费的机器高报一倍 —— 额度还剩一半就报红,而管理员没有任何办法
看出这是口径问题还是真的用超了。

**折算只发生在读取时。** `traffic_ledger` 与用户累计用量一个字节都不动,
改口径、改回去都不会毁掉任何历史数据。

**用户额度不受影响。** 那算的是用户自己用了多少,与主机怎么计费无关 ——
给用户的额度翻倍等于凭空多扣他一半。

**这是口径换算,不是精确值。** TCP/IP 头、重传、REALITY 与源站的握手,
以及系统更新、SSH 这些不走代理的流量都不在 sing-box 的计数器里,实际账单
通常还要再高几个百分点。想卡紧一点就把额度填得比商家给的略小。

## 节点落地协议:新增 Shadowsocks 2022(迁移 0014)

V4 第一块。节点在创建或编辑时可以选择落地协议,现在有两种:
`VLESS + REALITY`(原有)与 `Shadowsocks 2022`(新增)。

### 升级后什么都不会变

* 存量节点一律是 `VLESS + REALITY`,**渲染出的配置与升级前逐字节相同** ——
  不产生配置差异、不触发重新部署、订阅内容不变;
* 用户的 UUID、订阅地址、流量 ledger 与累计流量一个字节都不动;
* **节点二进制不用重新构建、不用重新分发**。Shadowsocks 在 sing-box 里是
  核心协议,不在任何构建标签后面,现有的二进制直接就支持。
  构建标签与 sing-box 版本都没改。

启动时会给存量节点与存量用户各补一把 Shadowsocks 密钥(日志里会说补了多少个),
跑过一次之后永远是空转。密钥是纯本地随机数,与节点跑什么协议无关 ——
缺了它,以后切协议会变成一个可能中途失败的操作。

### 想把某个节点改成 Shadowsocks

节点管理 → 编辑 → **落地协议** 选 `Shadowsocks 2022` → 保存 → **手动部署**。

保存之后不会自动部署,时机由你定。这一点很重要:

> **部署成功之前,订阅里仍然是旧协议的条目,现在的用户不会断线。**
> 面板只下发节点上已经生效的那一种协议。

部署那一下会重启 sing-box,断开这台机器上的全部在线连接;
部署完成后所有人都要**重新拉一次订阅**,不更新的客户端会一直连不上。
节点详情里「期望协议」与「节点上生效」分两行显示,不一致时会写明还没部署。

切回 `VLESS + REALITY` 需要该节点**已经完成过握手目标实测**
(详情里「扫描握手目标」,检测后应用)。没测过会被拒绝 ——
没实测的握手目标可能超过 8192 字节的记录上限,那会让所有人静默握手失败。

### Shadowsocks 节点要求节点时间准确

SS2022 的握手带时间戳,节点与真实时间相差超过约 30 秒时**全部用户都连不上**,
而 `sing-box check`、服务状态、端口监听与拨测**全部仍然通过** ——
拨测客户端跑在节点自己身上,与服务端共用同一个时钟,测不出这个问题。

所以部署事务开头多了一步「检查节点时钟」,超限直接中止,
此时节点上什么都还没动过。请确认节点开着 NTP:

```bash
timedatectl set-ntp true      # systemd 系
rc-service chronyd start      # Alpine / OpenRC
```

### 客户端要求

Shadowsocks 2022 的多用户靠 EIH,客户端的密码形如 `服务端密钥:用户密钥`。
不支持 EIH 的客户端(`ss-libev`、老版本 Clash)连不上,而且错误信息
通常只有一句「连接超时」。已知可用:sing-box、mihomo / Clash.Meta、
较新的 v2rayN 与 Shadowrocket。

另外 Shadowsocks 入站同时监听 TCP 与 UDP。防火墙只放行 TCP 的机器上,
网页能开但游戏和语音不通,而面板的所有检查都是绿的 —— 记得一并放行 UDP。

### 用户凭据

两种协议各有一份凭据,互不替代。用户详情的操作菜单里现在有两项:
「重新生成 UUID(VLESS)」与「重新生成密钥(Shadowsocks)」,
重置其中一份不影响另一份,也不影响订阅地址。
各自只会让跑对应协议的节点重新部署。

## 外部代理:把机场订阅并进自己的订阅(迁移 0015)

V4 第二块。侧栏「资源」下现在有两项:**自建节点**(原来的「节点管理」,
路由与数据一个字没改)与**外部代理**。

外部代理是「不属于本面板、不由本面板部署的成品线路」—— 机场订阅、
朋友给的一条 `ss://`。面板只负责登记与下发,让你的用户**只需要记住
一条订阅地址**,不管你今天用的是自建机器还是买来的机场。

### 升级后什么都不会变

新增三张表初始为空。在你导入任何东西之前,订阅内容、门户、
自建节点的一切行为与升级前完全一致。

### 加一条朋友给的链接

外部代理 → 添加代理 → 粘贴分享链接 → 解析 → 保存。

**推荐粘链接而不是手填**:面板会原样保留原始链接,订阅按分享链接下发时
直接透传它。按解析出的字段重新生成会把本面板不认识的参数悄悄丢掉
(混淆插件、`udp-over-tcp`、各家私有扩展),而丢掉之后用户能连上、
网页能开,只有 UDP 不通 —— 这种问题很难查。

### 导入一个机场

外部代理 → 导入订阅源。三步:

1. **填地址** —— 源名称、订阅地址、条目名前缀、新条目的默认等级;
2. **预览**(不落库)—— 逐条列出并可勾选;
3. **确认导入** —— 建源与首次导入是一个动作。

几件值得知道的事:

* **条目名前缀不自动加分隔符**。想要「[甲] 香港01」就在前缀末尾自己带一个
  空格,想紧贴就不带。前缀是渲染时拼的,改了立刻对全部条目生效;
* **公告条目默认不勾选**。机场订阅前几条常是伪装成节点的公告
  (「剩余流量:100.5 GB」「套餐到期:2026-09-01」),全量导入会让每个用户的
  客户端里多出几条永远连不上的「节点」。识别规则一定会误伤,所以它们
  **仍然全部列出**,由你自己决定;
* **不支持的协议会按类型报数**(「跳过 3 条:VMess 2 条、Trojan 1 条」)。
  本版本只落库 Shadowsocks;
* **没勾选的条目也会入库**,标记为「已排除」且不进订阅。不入库的话,
  下次同步它们会作为「新增」再进来一遍,你每次都得重新排除。

订阅地址含 token,等同密码:主密钥加密存储,**永不回显、不进审计日志**。

### 同步会做什么、不会做什么

* 按上游最新列表更新地址与凭据;
* 机场改节点名、轮换密码、换域名,都会被认成**同一个节点**而不是新增
  (匹配靠 `协议|地址|端口` 的指纹,以及「同一个源里的原始名」这个二级键);
* 你改过的展示名**不会**被上游盖回去(改的那一刻自动锁上,列表里显示
  「已锁定 N 项」)。想让它重新跟随上游,把展示名清空即可;
* **上游消失的条目不会立刻下架**。机场订阅接口抽风返回部分列表是常事,
  一次抽风就抹掉用户订阅里的节点、下次同步又回来 —— 用户看到的是节点
  忽有忽无,而这个现象无法复现。连续 **3 轮**没出现才自动退出订阅;
* **永远不自动删除**。删掉就丢了你配的展示名、等级、排序与备注,
  机场恢复后要全部重配;
* 重新出现时计数归零,但**订阅开关不自动恢复** —— 连续三轮消失通常意味着
  那个节点真的下线了,你多半已经据此调整了别的东西;
* **同步失败时一条都不改**。

自动同步默认关。打开之前建议先手工同步一次看看结果。

### 到期

源级与条目级各有一个到期时间。**源到期后它下面全部条目一起退出订阅** ——
机场账号到期后那些节点就是连不上的,留在订阅里只会让用户以为是自己的问题。
到期不删除任何数据,续期后自动回来。

到期前 7 天进仪表盘预警。源的到期取「你手工填的优先,没填才用上游给的」——
有些机场的 `expire` 头填得不准,让它无声覆盖你填的日期,
会在到期那天出现「面板说还有 20 天」。

### 关于流量

**外部代理统计不到流量。** 流量走的是上游的服务器,面板既没有它的 API
也没有 SSH。唯一能拿到的是订阅响应头里那个数字,而那是**整个机场账号的
总量**,按你的用户拆不开 —— 所以它只显示在源卡片上,
**绝不进任何用户的流量统计与额度**。

门户里外部代理单独一段「其他线路」,那一段不显示任何流量数字:
给一个 0 会被读成「我一点都没用过」,那比不显示更糟。
门户里也**不显示来源**(哪个机场)—— 用户知道了没有用处。

### 连通性检查

只做 DNS 解析 + TCP 连接,手工触发。**它只说明面板所在服务器能连到
那个端口**,不代表协议参数正确,也不代表你的用户能连上 ——
面板服务器与用户的网络路径完全不同。所以也不定时跑:
定时跑出一堆红灯只会让人再也不看这个列表。

## sing-box 多入站(V8)

一台落地机器现在可以有多个 sing-box 入口,各自的协议、端口、访问等级与
出口去向互不相干。原来那句「一个节点一个入站」不再成立。

### 升级做了什么

迁移 0019 把 `nodes` 上描述入站的那十几列(协议、三个端口、REALITY、SS、
TFO、链式)整体搬进新表 `node_inbounds`,**每台存量落地机器迁移成一行**,
`nodes` 上的原列就此冻结不再读写。中转规则与链式出站的落地从「指向一台机器」
改成「指向一个入口」。

### 升级后会发生什么变化

* **直连的存量节点渲染出的配置逐字节不变**,不会被判成待部署 ——
  入站 tag 沿用原来的 `vless-in` / `ss-in`;
* **已启用链式出站的节点会被判成待部署一次。** 链式从 `route.final` 改成
  `route.rules` 按入站分流,配置形状变了。那一次部署会重启 sing-box,
  踢掉在线连接,但配置行为完全等价 —— 挑个时机点一下即可;
* **每个用户能用的机器与入口一个都不变。** 迁移出来的入口等级一律填普通组
  (不是继承机器的等级)—— 继承会让 `user_nodes` 的额外授权凭空作废;
* 编辑节点的表单里不再有协议、代理端口与 TCP Fast Open,它们移到了
  节点详情的「入口」里,一条一行。新建节点时仍然填 —— 那是第一个入口。

### 升级后可以做的事

在节点详情 →「入口」→「新增入口 → sing-box 入口」加第二个入口:
换一个端口、换一种协议、给它单独的访问等级,或者让它单独链到别的落地。
**加完不会自动部署** —— 那会重启 sing-box 把这台机器上全部入口的人一起
踢掉,时机由你定。

### 关于流量

**流量拆不到入口。** sing-box 的用户计数器里没有入站这一维:同一个用户在
同一台机器上的流量是所有入口的合计。按机器、按用户看的数字仍然完全准确,
但「他在 8443 那个入口用了多少」这个问题答不了 —— 不是暂时没做。

## 访问等级降到入口(V8 之后的增量)

原来机器和入口各有一档访问等级,两层取交集。现在**只有入口有等级** ——
机器本身不接受任何连接,入口才接受。

### 升级做了什么

迁移 0020 先把每台机器的等级搬到它的入口上,再重建两个可见性视图。
`nodes.access_tier_id` 就此冻结。

**搬这一步不能省。** 不搬的话,升级后一台原本 VIP 的机器,它的入口全是
普通组,于是那台机器对全体用户敞开 —— 而你什么都没做过,面板也不会报错。

### 升级后会发生什么变化

* **每个用户能用的入口一个都不变。** 原来是「机器等级 ∩ 入口等级」,
  而入口等级此前一律是普通组;现在是「入口等级」,而入口等级刚从机器搬过来
  —— 两边算出来完全相同;
* 编辑节点的表单里不再有「访问等级」,它移到了「入口」里,一条一行。
  同一台机器现在可以有一个对所有人开放的入口和一个只给 VIP 的入口;
* **用户详情里对整台机器的「额外授权」现在穿透入口等级** ——
  它的意思就是「这台机器给他用」,包括上面全部入口。原来它只越过机器那一层,
  于是授权一台只有 VIP 入口的机器等于什么都没做,而面板不会提示;
* 节点列表的「等级」列变成这台机器上入口等级的汇总(可能是「普通组 / VIP组」),
  中转机显示「转发规则各自设定」。

### 入口页也合并了

sing-box 入口与 nginx 转发入口原来是两张表,现在合成一张,带类型列。
操作按钮按类型分成两行,各带一句后果:sing-box 那一行改了要重启服务、
会踢掉这台机器上**全部入口**的在线连接;nginx 那一行只 reload,
在途连接一条不断。

「部署」与「安装 sing-box」也从节点详情右上角移到了入口 Tab ——
部署下发的正是那一屏上列着的东西。顶栏只留一个跳过去的入口,
待部署时它会写成「待部署 · 去入口」。

## 外部代理不再只收 Shadowsocks(V9)

**没有迁移,存量记录一行不动。** `external_proxies.protocol` 本来就没有
CHECK 约束,协议参数本来就存成一份 JSON —— 加字段是向后兼容的。

现在收 Shadowsocks、VMess、VLESS、Trojan、Hysteria2 与 TUIC。
但「能进订阅」与「能当落地」不是一回事:

| | 进订阅给用户直连 | 当某个入口的出口 | 被 nginx 透传 |
| --- | --- | --- | --- |
| Shadowsocks / VMess / VLESS / Trojan | 能 | 能 | 能 |
| Hysteria2 / TUIC | 能 | **不能** | **不能** |

后两列的限制不在协议身上,在**我们这一侧**:节点上的 sing-box 是精简构建
(为了 128MB 的机器,不含 `with_quic`),拨不动 QUIC;nginx 透传只搬 TCP 字节,
而这两种是纯 UDP。用户自己的客户端是完整构建,所以它们照常下发、照常能用。
选出口和选转发落地时面板**直接不列出**它们,并说明少了几条、为什么。

### 顺手修掉的一个老问题

**`chacha20-ietf-poly1305` 这类传统 AEAD 的机场线路,以前登记得进来、
连通性检查是绿的、订阅也正常,唯独被设成某个入口的出口时部署会失败并回滚。**
原因是两处各有一张加密方法表,而渲染那一张只认 SS2022 —— 那是「我们自己的机器
跑什么」的答案,不该拿来校验别人的线路。现在客户端那张表只有一份。

### 加线路的方式变了一点

Shadowsocks 之外的协议**只能粘分享链接**,不能手工逐字段填。面板不去拼
这类链接:VMess 的 base64(JSON)、VLESS/Trojan 的查询串各家写法都不同,
拼出来的那条丢掉的正是面板没解析的那些参数,而丢掉之后用户能连上、
网页能开,只有某些场景不通。

### 中转到外部代理的两处修正

* `vmess://` 与旧式 `ss://`(整体 base64 那种)的地址藏在正文里,不在 URI
  语法里。以前会把整块 base64 当成地址换掉,产出一条连不上也不像链接的东西 ——
  **旧式 ss 那一支在只支持 Shadowsocks 的版本里就已经是错的**;
* 开了 TLS 但链接里没写 `sni` 的线路,经中转之后客户端会拿中转主机的名字去握手,
  落地直接拒绝。现在会把原本隐含的那个名字显式补进链接与出站配置。

## 日常升级(V2 之后)

```bash
bash <(wget -qO- https://raw.githubusercontent.com/KJoner/litebox/master/scripts/litebox-install.sh)
```

再跑一遍就是升级:依赖不重装,数据库与主密钥不动,升级前自动备份。

升级后确认:

```bash
systemctl status litebox
journalctl -u litebox -n 30
curl -s http://127.0.0.1:8080/api/health
```

节点上的 sing-box **不会**因为主控升级而改变。需要重新下发节点二进制时,
在节点详情里点「安装」。
