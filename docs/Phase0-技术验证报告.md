## 3. 必须修改设计的六个发现

### 3.1 REALITY 握手目标存在 8192 字节硬上限(严重)

最初使用 `www.microsoft.com` 作为握手目标,所有连接均失败,服务端只报一句
`REALITY: processed invalid connection`,不给任何原因。

排查结果:REALITY 认证本身是**成功**的(trace 日志显示 `hs.c.conn == conn: true`,
short_id 与客户端版本均匹配)。失败发生在之后的"窃取目标站证书"阶段。
`metacubex/utls` 的 `reality.go` 定义 `realitySize = 8192`,当目标站返回的任何一个
TLS 记录超过该值时直接放弃握手:

```
if handshakeLen > int(realitySize) { // too long
    break f
}
```

实测各候选目标从洛杉矶出口的最大 TLS 记录长度:

| 目标 | 最大记录 | 可用性 |
|---|---|---|
| www.cloudflare.com | 2,672 | 可用 |
| addons.mozilla.org | 4,133 | 可用 |
| www.apple.com | 4,738 | 可用 |
| dl.google.com | 5,021 | 可用 |
| gateway.icloud.com | 5,814 | 可用 |
| www.microsoft.com | 8,273 | **不可用** |
| www.bing.com | 8,340 | **不可用** |

微软系站点使用 RSA 证书链,体积超限;其余站点多为 ECDSA 证书,余量充足。

同一目标从不同出口测得的结果不同(`www.apple.com` 在本地 Windows 为 3,373,
在洛杉矶节点为 4,738),因为 CDN 会按地域下发不同证书链。

**对设计的要求:**
- 节点管理的"验证握手目标"必须**实际发起一次 TLS 1.3 握手并逐条测量记录长度**,
  不能只做 DNS 解析或端口连通性检查;
- 检测必须**在节点本机执行**(通过 SSH),不能在主控执行;
- 判定条件:协商出 TLS 1.3、密钥交换组为 X25519、所有记录 ≤ 8192 字节;
  建议同时要求 ALPN 支持 h2;
- 内置一份默认可用目标清单,并在保存节点前强制校验通过。

本次已实现该检测工具(`phase0/statsprobe/destcheck.go`),可直接移植进 Phase 2。

### 3.2 `sing-box check` 的校验范围远小于预期(严重)

原计划把 `sing-box check` 当作配置正确性的守门人。实测它只保证"配置能被解析并实例化",
不保证业务语义正确。两个已确认的盲区:

**盲区一:任意字符串都是合法 UUID。**
`sing-vmess/vless/service.go:44-46`:

```go
userID, err := uuid.FromString(userUUIDList[i])
if err != nil {
    userID = uuid.NewV5(uuid.Nil, userUUIDList[i])   // 回退:对字符串做哈希
}
```

写入 `"not-a-valid-uuid"` 时 `check` 通过、服务正常启动,sing-box 会用哈希派生出一个
可用的 UUID。若面板因缺陷写入空串或占位符,等于凭空产生一个**能正常上网的意外凭据**。

**盲区二:`flow` 字段只在连接时校验,配置期完全不检查。**
`service.go:86` 的 `unknown flow` 错误发生在握手过程中。实测把 `flow` 改成
`xtls-rprx-direct` 后:`check` 通过 → systemd active → 端口正常监听 →
**所有用户连接全部失败**。

这意味着"配置校验通过 + 服务已启动 + 端口在监听"这套健康检查会把一个完全不可用的
节点判定为健康。

**对设计的要求:**
- 面板必须在配置生成阶段自行强校验 UUID 格式、flow 取值、用户代码格式,
  不得依赖 `sing-box check`;
- 部署事务的健康检查**必须包含一次真实的 VLESS 拨测**;
- `sing-box check` 保留在流程中,但定位下调为"第一道粗筛"。

第 7 节的部署事务实测中,场景 4 正是靠拨测发现故障并成功回滚的。

### 3.3 统计白名单与用户列表不一致会导致静默计费失效(严重)

`experimental/v2rayapi/stats.go:71`:

```go
countUser := user != "" && s.users[user]
```

用户必须同时出现在 `experimental.v2ray_api.stats.users` 白名单中才会被计数。

实测构造 inbound 有两个用户、`stats.users` 只列一个的配置:
`sing-box check` 通过,两个用户都能正常上网,但 user_000002 **完全没有任何流量记录** ——
不报错、不告警、没有任何异常迹象。对一个以流量计费为核心的面板,这是最危险的失效模式。

**对设计的要求:**
- 配置生成必须由**同一份用户列表**同时渲染 `inbound.users[]` 与
  `experimental.v2ray_api.stats.users`,二者不允许由不同代码路径产生;
- 配置生成后增加断言:两个集合必须完全相等,不等则拒绝部署;
- 部署后的验收检查中,加入"该节点应有计数器的用户数"与实际用户数的比对。

### 3.4 仅靠"计数器变小"判定节点重启会漏算(严重)

原设计的基线差值法为:`增量 = 当前计数器 - 上次基线`,并在
`当前计数器 < 基线` 时判定为重启。该规则存在一个会造成**大额漏算**的场景:

```
同步(计数器=1MB,基线记为 1MB)
  → sing-box 重启,计数器归零
  → 产生 4MB 流量,计数器=4MB
  → 同步:4MB > 1MB,不触发回退判定
  → 增量被算成 4MB - 1MB = 3MB
```

实测漏算 1,007,534 字节 —— 正好等于重启前的计数值。注意漏算量不是"几秒钟的流量",
而是**整个重启前计数值**,金额可以很大。

修正方案:用 `GetSysStats` 返回的 `Uptime` 反推 sing-box 进程的启动时刻,
以两个独立信号判定换代,任一命中即把该节点所有基线归零:

1. 启动时刻前移超过容差(实测容差取 3 秒即可,15 秒过于宽松会漏判);
2. `Uptime` 小于两次同步的实际间隔(进程若在上次同步时已存在,uptime 必然不小于间隔)。

`计数器 < 基线` 保留为第三道兜底。修正后同一场景实测入账 4,011,696 字节,累计
5,019,230 = 1,007,534 + 4,011,696,完全正确。

此外,面板自己触发的重启属于已知事件,应在部署事务内**显式重置基线**,
不依赖任何推断 —— 这可以消除绝大多数场景下的判定风险。

### 3.5 未同步窗口内的流量不可恢复(设计约束,非缺陷)

实测:产生 2MB 流量后不同步直接重启,该 2MB **永久丢失**,无任何补救手段。
sing-box 的计数器是纯内存的 `atomic.Int64`,进程退出即消失。

这为"所有重启前必须先同步流量"提供了量化依据,并推出两条硬性要求:
- 部署事务的第一步必须是强制同步,**同步失败必须中止部署**(不能继续重启);
- 定时同步周期决定了意外重启(OOM、宿主机重启、崩溃)的最大损失窗口。
  60 秒周期意味着最坏情况丢 60 秒流量,对个人自用场景可以接受。

### 3.6 精简构建标签显著优于默认标签(优化项)

原计划为"上游默认标签 + `with_v2ray_api`"。实测 V1 功能集(仅 VLESS+REALITY+统计)
只需要 `with_utls`(REALITY 服务端已并入该标签)与 `with_v2ray_api`:

| 构建 | 二进制 | 空闲 RSS | cgroup 实占 | 8 并发峰值 RSS |
|---|---|---|---|---|
| 精简 `with_utls,with_v2ray_api` | 27.8 MB | 26.0 MB | 10.0 MB | 28.3 MB |
| 完整默认标签 + v2ray_api | 58.1 MB | 41.6 MB | 27.1 MB | 45.0 MB |

精简构建二进制体积减半、cgroup 实占内存降低约 63%。对 128MB 节点意义明显。

需保留的标签:`badlinkname,tfogo_checklinkname0`(上游默认标签的一部分,
与 `-checklinkname=0` 配套,缺失会导致构建失败)。

## 4. 用户级流量统计实测

计数器命名格式:`user>>>{用户代码}>>>traffic>>>{uplink|downlink}`

```
user>>>user_000001>>>traffic>>>downlink   3010230     (实际下载 3,000,000)
user>>>user_000001>>>traffic>>>uplink         771
user>>>user_000002>>>traffic>>>downlink   1007527     (实际下载 1,000,000)
user>>>user_000002>>>traffic>>>uplink         771
```

- 归属正确,两个用户互不串扰;
- 计量误差约 +0.34%,来自 VLESS/TLS 协议开销,属正常且符合预期(宁多勿少);
- 计数器**按需创建**:用户没有产生过流量时该计数器不存在,
  同步逻辑必须把"计数器缺失"与"计数器为 0"区别对待,不能当作归零处理。

gRPC 接口调用注意:sing-box 在 `v2rayapi/stats.go:21` 的 `init()` 中把服务名改注册为
`v2ray.core.app.stats.command.StatsService`,而其自带的客户端 stub 生成的调用路径是
`/experimental.v2rayapi.StatsService/...`,两者不一致。直接使用生成的 client 会报
`Unimplemented`。正确做法是用 `conn.Invoke` 显式指定
`/v2ray.core.app.stats.command.StatsService/QueryStats`。这是一个实现时必然会踩、
但文档里没有的坑。

## 5. 流量落库与重启一致性实测

原型实现:`绝对计数器 → 与基线比较求增量 → 单事务内写 ledger 并推进基线`。

| 场景 | 结果 |
|---|---|
| A 首次流量落库 | 4 条增量正确入账 |
| B 增量同步 | 只入账差值(计数器 6,026,654 − 基线 5,019,140 = 1,007,514) |
| C 幂等性(空跑两次) | 0 条新增,累计值不变 |
| D 重启前同步 → 重启 → 再同步 | 4,026,416 → 4,026,416,未丢失未回退 |
| E 重启后基线重建 | 正确识别换代,增量计算正确 |
| F 未同步就重启 | 2MB 永久丢失(见 3.5) |
| G API 不可达时同步 | 报错退出,数据库累计值完全未变 |

场景 G 尤其重要:同步失败时先读取、读取失败立即返回,不进入数据库事务,
因此不存在"把用户流量归零"的可能。这条性质必须在正式实现中保持。

ledger 采用 `(batch_id, node_id, user_code, direction)` 唯一索引,同一批次重复写入
会被数据库拒绝,提供幂等保证。

## 6. 低配节点内存实测

用 `systemd MemoryMax=128M`(cgroup v2 硬上限,超限即 OOM kill)模拟 128MB 节点:

| 配置 | 空闲 RSS | 16 并发峰值 RSS | OOM 次数 |
|---|---|---|---|
| 精简构建,无限制 | 26.0 MB | 28.3 MB(8 并发) | — |
| 精简构建,MemoryMax=128M | 25.4 MB | 29.9 MB | 0 |
| 精简构建,128M + GOMEMLIMIT=96MiB + GOGC=50 | 26.8 MB | 31.7 MB | 0 |

Go 运行时视角:`Alloc` 仅 2–3MB,`Sys` 12–17MB,goroutine 稳定 15 个。

**结论:128MB 节点完全可用,余量充足。**

需要注意 RSS 与 cgroup 计量的差异:RSS 约 26MB 中大部分是 mmap 进来的二进制页面
(精简构建二进制 27.8MB),而决定是否被 OOM kill 的 `memory.current` 只有 10–13MB。
这也解释了为什么减小二进制体积对低配节点收益明显。

GOMEMLIMIT 在本次负载下没有带来收益(反而略高,因 GC 更频繁)。建议默认不设置,
仅作为 128MB 节点出现问题时的备用手段。

## 7. 部署事务与回滚实测

实测事务流程(已按 3.2 的发现补强健康检查):

```
强制同步流量(失败即中止)
→ 上传临时配置
→ sing-box check(失败即中止,不重启)
→ 备份当前配置
→ 原子替换
→ systemctl restart
→ 健康检查一:systemd 状态 + 端口监听
→ 健康检查二:真实 VLESS 拨测      ← 新增,不可省略
→ 成功 / 失败则回滚上一版本并重启复验
```

| 场景 | 预期 | 实测 |
|---|---|---|
| 1 新增 user_000003 | 三个用户均可用 | 符合 |
| 2 删除 user_000002/3 | 仅 user_000001 可用 | 符合 |
| 3 REALITY 私钥非法 | check 拦截,不重启,配置不变 | 符合(返回码 2,服务全程未中断) |
| 4 flow 非法 | check 通过但拨测失败 → 回滚 | 符合(返回码 4,回滚后服务恢复) |

场景 3 证明了配置校验前置的价值:服务全程没有被重启,用户无感知。
场景 4 证明了拨测健康检查不可省略:如果只检查 systemd 与端口,这次部署会被判为成功,
而实际上全部用户已经断线。

## 8. 主控与节点的数据通路

验证方式:主控用 `golang.org/x/crypto/ssh` 建立 SSH 连接,把 `ssh.Client.Dial`
作为 gRPC 的 `ContextDialer` 注入,gRPC 流量直接跑在 SSH 通道内。

```
主控 --SSH(3022)--> 节点 --127.0.0.1:28080--> sing-box V2Ray API
```

实测(Windows 主控 → 洛杉矶节点):

```
SSH 建连           1320 ms
首次 QueryStats     316 ms
后续调用(复用连接)  154~158 ms
```

优点:节点上的 API 始终只监听 127.0.0.1,不需要在主控开本地转发端口,
也不需要在节点开放任何额外公网端口。

**对设计的要求:** SSH 建连成本约 1.3 秒,是单次调用的 8 倍。主控应按节点维护
**长连接并复用**,而不是每个同步周期重新建连。同时需要连接健康检查与自动重连。

## 9. 与原计划的差异汇总

| 原计划内容 | 修订 |
|---|---|
| 构建标签 = 上游默认 + `with_v2ray_api` | 改为精简标签 `with_utls,with_v2ray_api,badlinkname,tfogo_checklinkname0` |
| 节点操作"验证握手目标" | 明确为实测 TLS 记录长度,且必须在节点本机执行 |
| 所有配置替换前必须执行 `sing-box check` | 保留,但补充"面板自行强校验" + "部署后真实拨测" |
| 健康检查 = 检查 systemd 状态 + 检查端口 | 增加第三步:真实 VLESS 拨测 |
| 节点重启后重新建立统计基线 | 明确判定方法为 uptime 双信号 + 计数器回退兜底 |
| 流量统计策略 | 增加"stats.users 与 inbound.users 必须由同一数据源渲染并断言相等" |
| 节点字段 | 建议增加:`握手目标最大TLS记录长度`、`握手目标最后检测时间`、`singbox启动时刻` |
| 数据库表 | 建议增加 `node_instances` 表(记录节点进程启动时刻与最后同步时刻) |
